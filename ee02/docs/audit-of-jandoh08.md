# Accessibility audit: The Corner Loaf site by `jandoh08`

- **Site audited:** https://jandoh08.github.io/the-corner-loaf/
- **Date tested:** 16 November 2026
- **Audited by:** Samuel Attu
- **Standard:** WCAG 2.2, Level AA

## How I tested

- **Automated tools:** Chrome DevTools Accessibility & Lighthouse inspection, DOM/ARIA rule checks, and WebAIM Contrast Checker across all foreground/background colour pairs.
- **Keyboard:** Microsoft Edge and Chrome on Windows; did not touch the mouse and tested the full page journey from top to bottom using `Tab`, `Shift + Tab`, `Enter`, `Space`, and `Arrow` keys (placing an order, scrolling the weekly bakes table, opening and closing all four FAQ items, and submitting the contact form).
- **Zoom, text size and reflow:** Tested browser page zoom at `400%`, DevTools responsive viewport at `320px` CSS width, browser appearance font size set to **Very Large**, and Windows High Contrast (Forced Colors) themes (`Left Alt + Left Shift + PrtScn`).
- **Screen reader:** Windows Narrator (`Win + Ctrl + Enter`); tested heading navigation (`H`), table navigation (`T` and `Ctrl + Alt + Arrow` keys), button activation, and live form validation/submission announcements.
- **Pages and journeys covered:** Single-page bakery storefront (`index.html`), tested during both evening (`Closed · Opens tomorrow at 7am`) and live daytime (`Open now · Closes 5pm`) hours, covering: (1) checking today's available bakes and prices, (2) checking the weekly baking schedule in *This Week's Bakes*, (3) placing both a *Today's Order* and a *Pre-Order*, (4) reading the *Pre-Order FAQ*, and (5) sending an inquiry via *Send Us a Message*.

## Summary

Marcus, the rebuilt site already has a strong visual and structural foundation: colour contrast is clear and easy to read in bright light, the main sections are neatly organised, and order confirmations and phone number prompts are read out properly when someone submits a form. However, a few hidden barriers still shut out the exact customers you want to serve. Most importantly, a blind customer using a screen reader to check *This Week's Bakes* hears prices and baking days with only row numbers (`"row 2 of 7"`) instead of the bread names, and hears `"GH 28"` because the cedi symbol (`₵`) is skipped aloud. In addition, customers with low vision who set their browser font size to *Very Large* have product descriptions and prices cut off on screen, and anyone navigating with a keyboard instead of a mouse loses sight of which form box or submit button they are currently on. Fixing these issues is straightforward and will make checking bakes and placing orders effortless for every regular.

### 1. Screen reader users cannot tell which bread a price or baking day belongs to in "This Week's Bakes"

- **Principle, criterion and severity:** **Perceivable** — WCAG 2.2 **1.3.1 Info and Relationships** (Level A) — **Critical**. The Perceivable principle requires that information and relationships conveyed visually (such as which row label a price belongs to) also be available programmatically so assistive technology can present them in another modality.
- **Who it protects and how:** Blind and severely low-vision screen reader users (such as Marcus's regular customer). Sighted visitors scan left across a table row to see that `GH₵ 35` and `Tuesday & Friday` belong to `Sourdough Loaf`. Without programmatic row headers, a blind customer hears a disconnected stream of prices and days and cannot check the weekly schedule without abandoning the site.
- **What was found (`M1`):** In *This Week's Bakes* (`<table class="menu-table">` in `index.html` line 62 and `renderMenuTable()` in `js/script.js` lines 132–150), jumping to the table (`T`) and navigating down the *Price* or *Available* column (`Ctrl + Alt + Down Arrow`) in Windows Narrator announced only `"GH 28, row 2 of 7"`, `"gh 20, row 3 of 7"`. Every cell in each body row—including `product.name` in column 1—is created with `document.createElement("td")` instead of `<th scope="row">`, and the table has no `<caption>`.
- **Why it ranks #1:** Checking the weekly baking schedule and prices is the primary reason visitors open the site, and this Level A failure directly reproduces the blind customer's reported breakdown—blocking comprehension of the core content rather than merely slowing it down.
- **What to fix:** In `renderMenuTable()` (`js/script.js`), create the first cell in each row (`index === 0`) as `<th scope="row">` and the remaining three cells as `<td>`, and add `<caption class="sr-only">Weekly baking schedule and prices</caption>` inside `<table class="menu-table">`.

### 2. Product text is cut off when the browser font size is set to "Very Large"

- **Principle, criterion and severity:** **Perceivable** — WCAG 2.2 **1.4.4 Resize Text** (Level AA) and **1.4.10 Reflow** (Level AA) — **Significant**. The Perceivable principle protects users who must adapt text presentation to read it, ensuring that enlarging text up to 200% or viewing on a narrow viewport never truncates or hides content.
- **Who it protects and how:** Older customers and people with low vision who enlarge their browser's default font size (*Very Large*) rather than relying solely on full-page zoom. When product descriptions and prices are clipped at card edges, they cannot read what is on the shelf today.
- **What was found (`M9`):** At `400%` page zoom alone, nothing overlaps, but enabling Chrome/Edge's **Very Large** font size at `320px` width clips text across the *Available Today* product cards (`css/styles.css` lines 384–425). `.product-card` sets `display: flex; flex-direction: row; overflow: hidden;`, `.product-image` uses a fixed `rem` width (`var(--width-3xs)` = `5rem`, which expands with the root font size), and `.product-price` sets `white-space: nowrap;`.
- **Why it ranks #2:** Like Finding 1, this breaks the core bakery menu (*Available Today*), making product copy unreadable for low-vision visitors. It ranks just below Finding 1 because full-page zoom (`400%`) still works as a partial workaround, whereas Finding 1 fails completely for screen reader table navigation.
- **What to fix:** Allow `.product-card` and `.product-header` to wrap (`flex-wrap: wrap`), remove `overflow: hidden` from text containers (applying `border-radius` directly to `.product-image`), and constrain `.product-image` with `min(5rem, 30%)` (or stack cards vertically on narrow viewports) so enlarged text wraps freely without clipping.

### 3. Keyboard users cannot see which form field or submit button has focus, and submit buttons lose their borders in Windows High Contrast mode

- **Principle, criterion and severity:** **Operable** — WCAG 2.2 **2.4.7 Focus Visible** (Level AA), and **Perceivable** — **1.4.11 Non-text Contrast** (Level AA) — **Significant**. The Operable principle ensures every interactive control can be operated reliably without a mouse by keeping the user's current keyboard location unmistakable; Perceivable 1.4.11 ensures control boundaries remain distinguishable in every visual mode, including Forced Colors.
- **Who it protects and how:** Sighted keyboard-only users (people with motor impairments, hand tremors, repetitive strain injuries, or temporary injuries) and low-vision users who rely on Windows High Contrast themes. Losing sight of focus across all 10 interactive form controls turns placing an order or sending a message into guesswork.
- **What was found (`M5`, `M10`):** Tabbing through the page (`M5`) showed a clear focus ring on the table wrapper and FAQ buttons, but focus disappeared or became nearly invisible on all 8 `.form-field` inputs and both `.form-submit` buttons (*Submit Order* and *Send Message*). In `css/styles.css` (lines 285–307), `.form-field:focus` sets `outline: none;` with only a **1.46 : 1** border colour change (`#767676` to `#8b4513`) and a faint `0.12` shadow, while `.form-submit` has no `:focus-visible` rule and sets `border: 0;`, causing both submit buttons to appear completely borderless in Windows High Contrast mode (`M10`).
- **Why it ranks #3:** It affects every single control across both primary interactive workflows (ordering and contacting Marcus). It ranks below Findings 1 and 2 because the forms remain technically operable by keyboard, whereas Findings 1 and 2 obscure or clip core menu information.
- **What to fix:** Remove `outline: none` on `.form-field:focus`, add `outline: 2px solid var(--secondary-color); outline-offset: 0.25rem;` to `.form-field:focus-visible` and `.form-submit:focus-visible`, and replace `border: 0;` on `.form-submit` with `border: var(--border-width-thick) solid transparent;` so Forced Colors mode automatically draws a crisp system border.

### 4. Screen readers skip the Ghana Cedi symbol (`GH₵`) and announce generic, mismatched stock image descriptions

- **Principle, criterion and severity:** **Perceivable** — WCAG 2.2 **1.1.1 Non-text Content** (Level A) and **1.3.1 Info and Relationships** (Level A) — **Moderate**. The Perceivable principle requires text alternatives to convey accurate, equivalent meaning rather than misleading noise or dropped symbols.
- **Who it protects and how:** Blind screen reader users, who rely on accurate spoken currency and truthful image descriptions to understand prices and products.
- **What was found (`M2`):** Windows Narrator skips the Unicode Cedi symbol (`₵`, `U+20B5`) output by `formatPrice()` (`js/script.js` lines 59–62) across *Available Today*, the *Item* dropdown, and *This Week's Bakes*, reading `"GH 28"` instead of `"28 Ghana cedis"`. In addition, four distinct items (*Chin Chin*, *Butter Croissants*, *Banana Bread*, and *Meat Pies* in `js/script.js` lines 21–55) reuse `images/bofrot.jpg` with the generic `alt="A selection of freshly baked treats"`.
- **Why it ranks #4:** It degrades clarity on every price and four product cards, but users can still infer the numeric amounts and read the product names—making its severity Moderate rather than a complete blocker like Findings 1–3.
- **What to fix:** Provide an explicit spoken label for prices (e.g., `<span aria-hidden="true">GH₵ 28</span><span class="sr-only">28 Ghana cedis</span>` in cards and table cells, and `"28 Ghana cedis"` in `<option>` text), and set `alt=""` on decorative/stock thumbnails where the adjacent `<h3>` and `<p>` already describe the item.

### 5. Screen reader heading navigation (`H` key) skips all four FAQ questions, FAQ buttons read out `"plus"`, and there is no "Skip to main content" link

- **Principle, criterion and severity:** **Perceivable** (**1.3.1 Info and Relationships**, Level A), **Operable** (**2.4.1 Bypass Blocks**, Level A; **2.4.6 Headings and Labels**, Level AA), and **Robust** (**4.1.2 Name, Role, Value**, Level A) — **Moderate**. These principles protect efficient non-visual navigation so screen reader and keyboard users can skim structure by headings, bypass repeated blocks, and hear clean control names without decorative CSS noise.
- **Who it protects and how:** Screen reader users who skim pages using heading shortcuts (`H`) and keyboard-only users who must tab through repeated header/form controls to reach lower sections on every visit.
- **What was found (`M3`, `M4`):** Pressing `H` in Windows Narrator (`M3`) jumped straight from `<h2>Pre-Order FAQ</h2>` to `<h2>About The Corner Loaf</h2>` because the `<button class="faq-trigger">` elements (`index.html` lines 77–102) are not wrapped in `<h3>` headings. Tabbing to each FAQ button (`M4`) announced `"plus"` at the end of every question because `.faq-trigger::after { content: "+"; }` (`css/styles.css` line 240) is exposed to the accessibility tree. Finally, `<body>` has no skip link at the top of the page.
- **Why it ranks #5:** All four FAQ answers remain reachable by tabbing and reading linearly, so no user is blocked, but heading navigation efficiency and spoken clarity are reduced.
- **What to fix:** Wrap each `<button class="faq-trigger">` inside an `<h3>` heading, move the `+` indicator into `<span class="faq-icon" aria-hidden="true">+</span>` (or use CSS `content: "+" / "";`), and add `<a href="#main-content" class="skip-link">Skip to main content</a>` as the first element in `<body>`.

### 6. Contact form errors leave keyboard focus on the Submit button, and changing "Order Type" silently resets the selected item above it

- **Principle, criterion and severity:** **Understandable** (**3.3.1 Error Identification**, Level A) and **Robust** (**4.1.2 Name, Role, Value**, Level A) — **Moderate**. The Understandable principle protects users from unexpected state changes and helps them recover from input mistakes quickly; Robust 4.1.2 ensures validation state (`aria-invalid`) is communicated programmatically to assistive technology.
- **Who it protects and how:** Keyboard-only users, screen reader users, and people with cognitive or memory impairments who need clear, predictable error recovery and top-to-bottom form flow.
- **What was found (`M8`):** Submitting an invalid email (`abc@invalid`) in *Send Us a Message* (`js/script.js` lines 234–256) announces `"Please enter a valid email address"` via `role="status"`, but leaves keyboard focus on **Send Message** and never sets `aria-invalid="true"` or `aria-describedby="contact-status"` on `#contact-email`. In *Place an Order* (`index.html` lines 21–54), `#order-type` sits below `#order-item-select`; live daytime testing (`Open now · Closes 5pm`) confirmed that selecting `Sourdough Loaf (GH₵ 35)` and then switching `#order-type` between *Today's Order* and *Pre-Order* silently resets `#order-item-select` back to `"Select an item"` and updates `#order-form-help` without `aria-live`.
- **Why it ranks #6:** Error announcements already fire via `role="status"`, so users are notified that something went wrong—ranking this below core menu/focus blockers—but recovering from the error or switching order types creates avoidable friction.
- **What to fix:** In `initContactForm()` (`js/script.js`), set `emailInput.setAttribute("aria-invalid", "true")`, link `aria-describedby="contact-status"`, and call `emailInput.focus()` on error. In `#order-form` (`index.html`), move **Type** (`#order-type`) above **Item** (`#order-item-select`) and add `aria-live="polite"` to `#order-form-help`.

### 7. Personal form fields lack autofill (`autocomplete`), required fields have no visual marker, and WhatsApp/email contact details are plain text

- **Principle, criterion and severity:** **Perceivable** (**1.3.5 Identify Input Purpose**, Level AA) and **Understandable** (**3.3.2 Labels or Instructions**, Level A) — **Recommendation / Minor**. Perceivable 1.3.5 allows browsers and assistive tools to recognise personal data fields for autofill; Understandable 3.3.2 ensures users know which inputs are mandatory before hitting Submit.
- **Who it protects and how:** People with motor impairments, dyslexia, or memory difficulties who rely on browser autofill to avoid repetitive typing errors across two forms, sighted users checking which fields are mandatory, and mobile visitors who expect phone/email details to be tappable links.
- **What was found:** In `index.html`, `#order-name` (line 40), `#order-contact` (line 45), `#contact-name` (line 119), and `#contact-email` (line 123) have no `autocomplete` attributes; required fields use HTML `required` without a visual `*` or `(required)` indicator on their `<label>` elements; and `WhatsApp: 0551 000 000` and `Email: thecornerloaf@email.com` (`index.html` line 111) are plain text rather than `<a>` links.
- **Why it ranks #7:** Every form and contact detail is still readable and usable, making these lower-severity usability and compliance improvements to address after Findings 1–6.
- **What to fix:** Add `autocomplete="name"`, `autocomplete="tel"`, and `autocomplete="email"` to the personal inputs; add a visual required indicator (`(required)` or `<span aria-hidden="true">*</span>`) to required labels; and wrap the contact details in `<a href="https://wa.me/233551000000">` and `<a href="mailto:thecornerloaf@email.com">`.

## What works well

- **Colour contrast across the entire palette (WCAG 1.4.3 & 1.4.11):** Verified with the WebAIM Contrast Checker. Every text element passes Level AA (`4.5:1`), and almost all pass Level AAA (`7.0:1`), including the hero title (`#ffffff` on `#8b4513`, **7.10 : 1**), hero subtitle (`#f5deb3` on `#8b4513`, **5.40 : 1**), body text (`#222222` on `#f9f9f9`, **15.11 : 1**), section headings (`#4a2c0a` on `#f9f9f9` / `#f5deb3`, **12.05 : 1** / **9.65 : 1**), muted text (`#444444` on `#ffffff` / `#f9f9f9`, **9.74 : 1** / **9.25 : 1**), error messages (`#b3261e` on `#f9f9f9`, **6.21 : 1**), and unfocused input borders (`#767676` on `#f9f9f9`, **4.31 : 1**).
- **Page language, title, landmarks, and main heading order (WCAG 3.1.1, 2.4.2, 1.3.1, 2.4.6):** `<html lang="en">` and a descriptive `<title>` are set; `<header>`, `<main>`, `<section>`, and `<footer>` landmarks are used properly; and main section headings step cleanly from `<h1>` to `<h2>` to `<h3>` without skipping levels.
- **320px responsive reflow and isolated table scrolling (WCAG 1.4.10, Manual test `M11`):** At `320px` CSS width, the page reflows into a single vertical column with no page-level horizontal scrolling. Only the *This Week's Bakes* data table scrolls horizontally inside its `.table-wrapper` (`tabindex="0"`), which is an allowed two-dimensional exception under WCAG 1.4.10.
- **Order confirmation and contact status live regions (Manual tests `M6` & `M8`):** Submitting *Place an Order* (tested for both *Today's Order* and *Pre-Order*) with the keyboard appends the order to `#order-list` (`aria-live="polite"`), which Windows Narrator announces clearly and immediately without reading the `|` separator symbols aloud; likewise, `#contact-status` (`role="status"`) immediately announces contact form status and error messages aloud.
- **Phone number format validation (Manual test `M7`):** Entering an invalid phone number (`123`) in `#order-contact` and pressing `Enter` displays a clear browser validation popup and reads out the required format (`0551 000 000`) from the `title` attribute via Windows Narrator.
- **FAQ accordion keyboard activation and focus ring (Manual tests `M4` & `M5`):** The FAQ questions are built with native `<button type="button">` elements (`aria-expanded`, `aria-controls`, and `hidden` panels). Keyboard testing confirmed a clear focus ring on the table wrapper and FAQ buttons, and pressing `Enter` or `Space` toggles the answers reliably while announcing `"expanded"` / `"collapsed"`.
- **Tap target sizes (WCAG 2.5.8):** All inputs (`44px` height), buttons (`42.7px` height), and FAQ triggers (`25.6px` height) exceed the `24×24 CSS pixel` minimum target size.

## Not tested, and limits of this audit

- **Mobile screen readers on physical phones:** Tested with Windows Narrator on a Windows desktop browser; did not test with TalkBack on Android or VoiceOver on iOS.
- **Speech-input / voice-control software:** Did not test with Dragon NaturallySpeaking or Windows Voice Access.
